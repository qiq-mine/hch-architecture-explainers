# 内容模型与场景选型指南

先从原始资料提取事实，避免先选组件再硬塞内容。

| 提取项 | 记录问题 |
| --- | --- |
| **受众** | 谁需要理解，已有何种背景？ |
| **核心问题** | 展示完成后必须能回答什么？ |
| **实体** | 服务、用户、数据、基础设施分别是什么？ |
| **关系** | 谁调用、依赖、读写或拥有谁？ |
| **状态** | 处理前后发生什么变化？ |
| **边界** | 信任、网络、团队或部署边界在哪里？ |
| **证据** | 哪些来自事实，哪些仍是推断？ |
| **发起和可发现性** | 谁或什么启动它，相关能力如何被发现或选中？ |

## 五大标准图表场景选型与提问清单 (Recipes)

根据系统要回答的核心问题，将内容结构化映射到 5 种标准模式之一：

### 1. Architecture (系统架构)
- **核心问题**：系统包含哪些核心组件？边界和协议是什么？外部依赖在哪？
- **实体清单**：接入层、计算服务、存储集群、第三方 API、安全信任域；
- **关键关系**：同步 RPC/HTTP 调用、专网与公网隔离线、数据持久化链路。

### 2. Workflow (工作流 / 协作)
- **核心问题**：任务如何从触发推进到完成？各角色如何协作？异常如何恢复？
- **实体清单**：触发源（人类/定时器/Webhook）、执行阶段、质量检查网关、分支决策、重试队列；
- **关键关系**：阶段推进条件、失败回退路径、告警与人工审批介入点。

### 3. Sequence (时序 / 调用链)
- **核心问题**：一次具体请求在各服务间的传递顺序与时序耗时如何？
- **实体清单**：客户端、网关、鉴权中心、下游微服务、缓存、数据库；
- **关键关系**：同步调用与返回、缓存命中 vs 未命中回源分叉、异步消息触发。

### 4. Data Flow (数据流转 / 工程)
- **核心问题**：数据从哪里来、经过什么加工、存到哪里、被谁消费？
- **实体清单**：数据源系统、消息管道 (Kafka)、清洗/计算引擎 (Flink/Spark)、分层数仓 (ODS/DWD/DWS/ADS)、消费端 (BI/ML/API)；
- **关键关系**：实时流 vs 离线批量、血缘拓扑、敏感字段脱敏与 PII 边界。

### 5. Lifecycle (生命周期 / 状态机)
- **核心问题**：对象或能力处于什么状态？由什么事件驱动状态跃迁？终态是什么？
- **实体清单**：初始态、就绪态、运行/执行态、挂起/重试态、终态（成功/失败）；
- **关键关系**：事件驱动迁移条件、超时守卫、按需资源加载、质量门槛校验。

## 机制或生命周期的起点

对任何机制或生命周期，按固定叙述顺序建模：先写明发起者（用户、事件、调度器、服务或 host）及其能力可发现路径；再为每个阶段写出进入下一阶段的转换条件、触发事件或判断；最后写由此产生的状态变化。以 Skill 为例，host 先向模型提供已安装 Skill 的 `name`、`description`、`path` 轻量列表。用户可通过 `@`/`$` 显式点名，或在任务语义与 `description` 匹配时隐式选择；选中后模型才读取完整 `SKILL.md`。不要描述成 Skill 自己持续扫描，也不要笼统归因于 system prompt。

## 页面映射

| 内容类型 | 页面角色 | 读者获得的信息 |
| --- | --- | --- |
| **概念 (Concept)** | Hero、定义、术语卡 | 系统是什么、范围是什么、解决什么核心问题 |
| **关系 (Relationship)** | 分层图、依赖图、拓扑网格 | 组件如何连接、协议与信任边界 |
| **流程 (Flow)** | Stage、Slide、时序步进 | 状态怎样逐步变化、各阶段输入输出 |
| **权衡 (Tradeoff)** | 对比卡片、适用与限制面板 | 为何选择该方案、优势与代价 |
| **结论 (Conclusion)** | 总结区、行动项、设计启示 | 应记住或继续验证什么 |

## 划分节点原则

一个节点必须同时具备明确输入、可描述的状态变化和输出。若两个步骤只在配色、图标或文案装饰上不同，应合并；不要为填满页面而拆分。节点是语义阶段，而非视觉分页。

- **1–3 个语义节点**：使用正常纵向流式滚动。
- **4 个及以上语义节点**：使用横向 Slide，提供按钮、页码、左右方向键与触控手势。

当同一内容同时生成架构图与 Web 讲解时，为每个节点分配稳定 ID，并记录其对应的页面章节或 Slide。架构图保持主链路粒度，Web 可以把一个节点展开为多个细节步骤，但不得另起一套术语、顺序或回环含义。

## 示例：订单平台调用链

原始链路为“入口层 → API 网关 → 三个业务服务 → 消息队列 → 数据层 → 监控 → 故障回路”。可得到七个语义节点：

1. **入口层**：用户请求进入，得到已接收的访问意图。
2. **API 网关**：请求携带身份和路由规则，变为已鉴权、已分发调用。
3. **三个业务服务**：网关调用订单、库存、支付服务，形成可执行的业务结果。
4. **消息队列**：业务事件入队，变为可异步消费、可重试的任务。
5. **数据层**：服务与消费者写入或读取持久状态，输出一致的业务记录。
6. **监控**：指标、日志和追踪汇聚，输出可观测的健康信号。
7. **故障回路**：异常信号触发告警、重试或降级，输出恢复动作并反馈到入口与服务。

七个节点均有不同的输入、变化和输出，因此采用横向 Slide；若“监控”和“故障回路”在资料中没有独立变化，应合并后重新计数。
